## Story

**En tant que** DJ,
**je veux** que l'app réagisse proprement aux appels, aux débranchements et aux changements de périphérique,
**afin de** ne jamais entendre de son inattendu ni subir de plantage.

## Critères d'acceptation

1. **Interruption iOS (SF-18, RM-10, RM-56 ; 6.5 « Recevoir une interruption système (iPhone/iPad) »).** Début d'interruption : les deux moteurs passent immédiatement à STOP, positions conservées, y compris si un disque est tenu ; fin d'interruption : la sortie redémarre, rien ne reprend, START est nécessaire.
2. **Casque déconnecté iOS (D-04 ; 6.5 « Débrancher le casque (iPhone/iPad) »).** Sur `routeChanged(previousDeviceUnavailable: true)`, `stopAllMotors` est envoyé avant toute sortie sur le haut-parleur.
3. **Périphérique utilisé disparu (RM-56, D-04 ; 6.5 « Perdre le périphérique audio »).** Interface USB retirée (macOS) ou ancien périphérique indisponible (iOS) : aucun plantage, la nouvelle route du système est suivie, les moteurs passent à STOP, la reprise est manuelle.
4. **Changement volontaire de sortie (SF-16, D-04 ; 6.5 « Changer de périphérique de sortie sur Mac »).** macOS : nouveau périphérique par défaut, l'ancien restant connecté, éventuellement à une autre fréquence → le moteur audio redémarre sur la nouvelle sortie avec `outputSampleRate` mis à jour ; hauteur, vitesse nominale et positions inchangées ; les moteurs gardent leur état. iOS : un changement de route autre qu'une disparition ne change pas l'état des moteurs.
5. **Veille du Mac (0.3, RM-56 ; 6.5 « Mettre le Mac en veille »).** À la mise en veille, moteurs à STOP ; au réveil, sortie relancée, aucune reprise, positions conservées.
6. **Aucune sortie disponible (SF-82, D-35 ; 6.5 « Aucune sortie audio disponible »).** État « Sortie audio indisponible », horloge de secours (disques vivants, silence), interface utilisable, nouvel essai automatique toutes les 2 s et à chaque changement de route, sans redémarrer l'app ; à la réussite, horloge arrêtée puis sortie démarrée ; aucun moteur ne démarre.
7. **Nom de sortie à jour (6.5 « Brancher une interface audio USB »).** Le nom publié dans `AudioOutputStatus.running` est mis à jour à chaque changement de route ou de périphérique.
8. **Avis pour l'interface (UX §8.5).** L'hôte publie un avis observable à chaque transition qui demande un bandeau : interruption, sortie déconnectée, sortie indisponible, sortie retrouvée (avec son nom) ; 6.2 l'affiche.
9. **Politique isolée et testée (PRD 2.3-8).** La logique « événement système → action » est une fonction pure, testée sur macOS avec des événements simulés pour les deux plateformes ; le comportement sur matériel est vérifié en recette (6.3, PO-08, D-44).

## Dev Notes

### Contrats (Contracts/, ne pas modifier)

```swift
public enum AudioSystemEvent: Equatable, Sendable {
    case interruptionBegan, interruptionEnded
    case routeChanged(previousDeviceUnavailable: Bool)
    case configurationChanged, mediaServicesReset
    case systemWillSleep, systemDidWake
}
@MainActor public protocol AudioOutputHosting: AnyObject {
    var status: AudioOutputStatus { get }; var isRenderingAudio: Bool { get }
    func start(); func stop(); func suspend(); func resume()
}
```

`configurationChanged` n'a pas de paramètre : l'hôte vérifie lui-même si le périphérique utilisé est toujours présent (contexte passé à la politique).

### Politique (architecture §7.3, D-04) — règle unique

Un choix volontaire de sortie garde l'état des moteurs ; la perte d'une sortie, une interruption ou la veille les mettent à STOP ; la reprise est toujours manuelle.

| Événement | Plateforme | Action de l'hôte | Moteurs |
|---|---|---|---|
| `interruptionBegan` | iOS | `send(.stopAllMotors)`, sortie arrêtée, horloge de secours | STOP |
| `interruptionEnded` | iOS | horloge arrêtée, sortie redémarrée | inchangés (STOP) |
| `routeChanged(previousDeviceUnavailable: true)` | iOS | `stopAllMotors` avant toute sortie sur le haut-parleur, puis nouvelle route | STOP |
| `routeChanged(previousDeviceUnavailable: false)` | iOS | la sortie suit la nouvelle route | inchangés |
| `configurationChanged`, ancien périphérique toujours présent | macOS | reconstruction, `send(.outputSampleRate(new))`, redémarrage | inchangés, lecture continue |
| `configurationChanged`, périphérique utilisé disparu | macOS | `stopAllMotors`, reconstruction sur le nouveau périphérique par défaut | STOP |
| `configurationChanged` (fréquence) | iOS | reconstruction, `send(.outputSampleRate(new))` | inchangés |
| `mediaServicesReset` | iOS | reconstruction complète du graphe et de la session | STOP |
| `systemWillSleep` / `systemDidWake` | macOS | `stopAllMotors` / sortie relancée | STOP / inchangés |
| Aucune sortie, démarrage impossible | les deux | `.unavailable`, horloge de secours, essai toutes les 2 s et à chaque changement de route | inchangés |
| Arrière-plan (`scenePhase`) | iOS | `suspend()` (2.1, appelé par 6.2) | STOP |
| Fenêtre inactive | macOS | aucune | inchangés |

Chaque `send` issu d'une notification est d'abord ramené sur le fil principal (`Task { @MainActor in … }`) : il n'y a qu'un producteur de commandes.

### Avis pour l'interface (CA 8)

Proposition, sur le type concret (le protocole `AudioOutputHosting` n'a pas de canal d'événements) :

```swift
public enum AudioHostNotice: Equatable, Sendable {
    case interrupted                        // « Lecture interrompue par le système. Appuyez sur START pour reprendre. »
    case outputDisconnected                 // « Sortie audio déconnectée : les platines sont arrêtées. »
    case outputUnavailable                  // « Sortie audio indisponible. ScratchApp réessaiera automatiquement. »
    case outputAvailable(name: String)      // « Sortie audio disponible : <nom>. »
}
// AudioEngineHost
public private(set) var notice: (id: Int, value: AudioHostNotice)?   // observable ; id croissant
```

L'`AppModel` (6.2) lit cet avis sur l'hôte concret. Si l'architecte préfère l'ajouter au protocole `AudioOutputHosting`, le changement de contrat se fait dans cette story avec son accord (signalé dans la PR).

### Pièges connus

- **Fil des notifications** : `AVAudioSession` et `AVAudioEngineConfigurationChange` arrivent sur un fil quelconque ; relayer sur le fil principal avant toute action (R-07).
- **Un seul fil de rendu** pendant la reconstruction : horloge de secours arrêtée de façon synchrone avant `AVAudioEngine.start()` ; jamais les deux à la fois (`RoleGuard`).
- **STOP avant le haut-parleur** (CA 2) : `stopAllMotors` est appliqué au tampon suivant ; pour ne rien entendre sur le haut-parleur, couper la sortie (pause) **avant** que la nouvelle route ne rende, puis relancer.
- **Code iOS** (`#if os(iOS)`) compilé seulement par le build iOS de la CI : la politique reste hors des `#if` pour être testée sur macOS.
- **Veille** : `NSWorkspace.shared.notificationCenter`, pas le centre par défaut.
- **Langue (D-42)** : identifiants en anglais, `///` en français, `//` en anglais.

**Partie 2 — branchement dans l'hôte**

- **`AudioEngineHost`** exécute, dans l'ordre, les actions de `AudioSystemPolicy` pour chaque
  événement reçu sur le fil principal. Le contexte est tenu par l'hôte : sortie indisponible,
  interruption en cours, hôte suspendu, et présence du périphérique utilisé, fournie par la sortie.
  - `stopOutput` et `rebuildGraph` arrêtent la sortie et abandonnent son graphe. La sortie construit
    un graphe neuf, sur la sortie courante du système, à chaque démarrage.
  - `applyPendingCommands` (`pump()`) ne s'exécute que si aucun fil ne rend.
  - `startOutput` arrête l'horloge de secours, de façon synchrone, avant le démarrage. Son issue passe
    par `actionsAfterStart`.
  - `isRenderingAudio` suit l'état réel. Il est faux pendant la veille du Mac, et l'`AppModel` peut
    alors pomper.
  - Pendant une interruption, l'état est `.unavailable(reason: "Lecture interrompue par le système.")`
    et l'horloge de secours rend.
- **Nouvel essai (T4)** : minuterie (`Task`) de 2 s, armée tant que la sortie est indisponible, hors
  interruption et arrière-plan. Elle est annulée dès que la sortie démarre et par `stop()` ou
  `suspend()`. Chaque changement de route ou de configuration relance aussi un essai (politique).
  L'intervalle est injectable pour les tests (50 ms).
- **Avis (T5)** : `AudioEngineHost.notice: PostedNotice?` (`id` croissant, `notice`), observable. Il
  est défini sur le type concret : aucun changement du contrat `AudioOutputHosting`. La 6.2 le lit sur
  l'hôte concret.
- **iOS (T2)** : `AudioSessionController.startObserving()` écoute les notifications d'interruption,
  de changement de route et de réinitialisation des services média, sur la file principale. Elles sont
  transmises de façon synchrone. La traduction est en logique pure (`AudioSessionEvents`, valeurs
  brutes du SDK vérifiées par assertion), testée sur macOS. Le changement de catégorie est ignoré :
  l'hôte le provoque à chaque activation, et il relancerait un essai en boucle quand la sortie est
  indisponible. Après une réinitialisation des services média, le graphe est abandonné et la session
  est reconfigurée au démarrage suivant. `resume()` clôt une interruption dont la fin n'a pas été
  notifiée.
- **macOS (T3)**, recommandations de la gate de #88 :
  - `AVAudioEngineConfigurationChange` passe par la fenêtre de regroupement du moniteur, celle des
    notifications Core Audio : un changement de périphérique donne un seul `configurationChanged` ;
  - `deviceInUse` est fixé à chaque démarrage réussi, et remis à `nil` avant chaque essai ;
  - `OutputDeviceMonitor.currentDefaultOutputDevice()` passe par `OutputDevice.defaultOutput()` ;
  - l'ancienne sortie est arrêtée avant chaque démarrage ;
  - une notification d'un graphe abandonné est ignorée (compteur de génération).
- **Écoute** : la sortie écoute le système entre `start()` et `stop()` de l'hôte, y compris quand la
  sortie est indisponible. La gate de #84 relevait qu'aucun observateur n'existait dans l'état
  `.unavailable`.
- **Tests de l'hôte** (`AudioEngineHostSystemEventTests`, double `FakeOutput` partagé avec
  `AudioEngineHostTests`) : un test par CA de 1 à 8, plus la réinitialisation des services média, la
  traduction iOS et deux tests sur la sortie réelle (regroupement, périphérique utilisé).
- **Recette 6.3 (#44)**, sur matériel :
  - appel entrant avec un disque tenu ;
  - casque débranché ;
  - interface USB retirée puis rebranchée ;
  - changement de sortie dans les Réglages du Mac ;
  - veille et réveil ;
  - démarrage sans sortie, puis branchement.
