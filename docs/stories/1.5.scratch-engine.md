## Story

**En tant que** DJ,
**je veux** que les deux platines et la table de mixage soient rendues ensemble en temps réel,
**afin de** jouer A et B simultanément sans que l'une perturbe l'autre.

## Critères d'acceptation

1. **Cycle de rendu (contrat 0.2).** `ScratchEngine.render` vide la file de commandes SPSC au début de chaque appel (tant que la file de retour a de la place), rend N trames stéréo par blocs de 512 au plus (physique 1.1 → voix 1.3 → table 1.4, deux platines) et publie un instantané complet (`EngineSnapshot`) à la fin de chaque appel.
2. **Indépendance (SF-64, RM-51 ; 6.8 « Les platines sont indépendantes », « Scratcher A pendant que B joue »).** Aucune commande d'une platine ne modifie l'autre : instantané et signal de B identiques, à l'échantillon près, qu'on scratche A ou non.
3. **Chargement (SF-03, SF-13, RM-01, RM-57 ; 6.6 « Le CUE est propre à chaque son », 6.8 « Charger le même son sur les deux platines », 6.2 « Démarrer sans fichier »).** Après `load` : tête à 0 s, moteur arrêté, CUE effacé, repère aligné (`stickerAngle ≡ 0`). Un même clip se charge sur A et B sans copie, avec positions, moteurs et CUE propres. Une platine vide n'émet aucun son, même plateau en rotation. L'ancien clip passe par la file de retour (jamais libéré sur le fil audio).
4. **Gestes (SF-06 à SF-10, RM-03).** Les commandes `touchBegan/Moved/Ended` pilotent la tenue et l'angle cible du disque de la platine visée ; le toucher est prioritaire sur le moteur ; un second `touchBegan` sur un disque tenu est ignoré.
5. **CUE (P1, SF-13 ; 6.6).** SET CUE mémorise la tête ; CUE y ramène sans changer l'état du moteur ; sans CUE, retour à 0 s ; disque tenu, SET CUE mémorise la position courante et le rappel ré-ancre le geste sur la position du CUE, sans clic (fondu de 1.3) : le disque reste sous le doigt et suit ses mouvements depuis le CUE (6.6 « Définir un CUE pendant que je retiens le disque », « Rappeler le CUE pendant que je retiens le disque »).
6. **Needle drop (P1, SF-71 ; 6.11).** `seek` est ignoré tant que le disque est tenu ; sinon il est lissé en 5 ms au plus et ne change pas l'état du moteur (6.11 « Positionner la tête sur l'aperçu (needle drop) », « Needle drop ignoré pendant que je retiens le disque »).
7. **Repère (SF-69, RM-13, IC-09 ; 6.11 « Le repère suit le disque », 6.3 « Lancer le son depuis le repère »).** `stickerAngle ≡ 0 (mod 2π)` quand la tête est au CUE (ou à 0 s sans CUE), en lecture comme après une sortie de butée, un rappel de CUE ou un needle drop.
8. **Arrêt général (RM-56).** `stopAllMotors` met immédiatement les deux moteurs à STOP, sans rampe, positions conservées ; un disque tenu reste tenu.
9. **Temps réel (NFR2).** 10 000 rendus de 256 trames, deux platines à ±16× et un flux continu de commandes (gestes, mixeur, CUE), ne font aucune allocation sur le fil de rendu (compteur d'allocations sous Linux et macOS) ; aucun verrou ; file pleine : `send` renvoie `false` sans bloquer et rend le +1 du clip ; un clip remplacé n'est jamais libéré dans le fil de rendu.
10. **Scénario hors ligne déterministe (NFR11, base de 2.4).** `ScratchScenario` (dans `Diagnostics/`, compilé dans `ScratchCore`, hors cible de test), paramétré par le clip et rejouable sur n'importe quel moteur de rendu, enchaîne START → vitesse nominale → tenue immobile → scratch avant et arrière (baby scratch) → relâchement → coupures au crossfader → coupure momentanée → STOP, et produit un rapport de vérifications nommées : silence pendant la tenue immobile et plateau en rotation, signe de la vitesse conforme au geste, vitesse du plateau retrouvée dans le temps de rattrapage, voie fermée ≤ −60 dBFS, crête ≤ 0 dBFS, aucune valeur NaN. Un même flux de commandes produit la même sortie à l'échantillon près.
11. **Charge (NFR3, indicatif).** Un rendu de 256 trames, deux platines à 16× avec anti-repliement, prend 30 % au plus de la durée du tampon (5,3 ms) sur Mac Apple Silicon ; mesure publiée dans le journal de test (non bloquante en CI).

### Scénarios de vérification

```gherkin
Feature: ScratchEngine (48 kHz, tampons de 256 trames)

  Scenario: Même son sur A et B (RM-57)
    Given un clip de 4 s chargé sur A puis sur B
    When A démarre et B reste arrêtée
    Then A avance et B reste à 0 s
    And un SET CUE sur A ne crée aucun CUE sur B
    And le clip n'est libéré qu'après déchargement des deux platines et drainReleasedClips()

  Scenario: Rappel du CUE disque tenu (6.6)
    Given un CUE à 12 s sur A, le disque A tenu à 20 s
    When recallCue(.a) est appliqué
    Then la position de A passe à 12 s avec un fondu ≤ 5 ms
    And le disque reste tenu
    When le doigt avance d'un quart de tour
    Then la position de A vaut 12,45 s ± 10 ms

  Scenario: Aucune allocation (NFR2)
    Given deux platines chargées, moteurs actifs, gestes continus à ±16×
    When 10 000 tampons de 256 trames sont rendus
    Then le compteur d'allocations du fil de rendu reste à 0
```

### Contrat public (Contracts/ et Engine/, signatures figées)

```swift
public protocol EngineControlling: AnyObject {              // fil de contrôle uniquement
    @discardableResult func send(_ command: EngineCommand) -> Bool
    func latestSnapshot() -> EngineSnapshot
    @discardableResult func drainReleasedClips() -> Int
    func pump()                                              // seulement si aucun fil ne rend
}
public final class ScratchEngine: EngineControlling, @unchecked Sendable {
    public static let commandCapacity: Int        // 1024
    public static let releaseCapacity: Int        // 64
    public static let maximumBlockFrames: Int     // 512 ; render découpe au-delà
    public init(outputSampleRate: Double = 48_000)
    public func render(frameCount: Int, left: UnsafeMutablePointer<Float>, right: UnsafeMutablePointer<Float>)
}
public enum EngineCommand: Equatable, Sendable {
    case load(DeckID, AudioClip), unload(DeckID), motor(DeckID, on: Bool), speed(DeckID, TurntableSpeed)
    case pitch(DeckID, Double), resistance(DeckID, Double)
    case touchBegan(DeckID, angle: Double, time: Double)
    case touchMoved(DeckID, angle: Double, time: Double, predicted: Bool = false)
    case touchEnded(DeckID, time: Double)
    case setCue(DeckID), recallCue(DeckID), seek(DeckID, seconds: Double)
    case startDuration(Double), brakeDuration(Double), slipmatCatchUp(Double)
    case crossfader(Double), crossfaderCurve(Double), hamster(Bool), lineFader(DeckID, Double)
    case momentaryCut(DeckID, open: Bool)
    case stopAllMotors, outputSampleRate(Double)
}
```

### Comptage d'allocations (CA 9) — point d'attention

Swift ne fournit pas de compteur d'allocations portable. Options, à choisir par James :

1. **Interposition de `malloc`** (méthode des tests d'allocation de SwiftNIO) : une petite bibliothèque C de test qui redéfinit `malloc`, `calloc`, `realloc`, `free`, `posix_memalign` et compte les appels quand un drapeau thread-local est levé autour de `render`. Demande une **cible C de test dans `Package.swift`** : à faire valider par l'architecte (Winston, via l'orchestrateur) avant de coder.
2. **macOS seulement** : remplacer les pointeurs de fonction de `malloc_default_zone()` pendant le test ; Linux : contrôle plus faible par `mallinfo2()` (pas de croissance), complété par la revue QA.
3. **Revue et Instruments** : en dernier recours, documenté comme réserve de la gate QA.

Signaler le choix dans la PR ; une modification de `Package.swift` sans accord de l'architecte est interdite (`TEAM.md`).

### Règles temps réel (architecture §6.1)

Aucune allocation (ni `Array` créé ou agrandi, ni chaîne, ni classe instanciée, ni closure capturante, ni `any P`, ni générique non spécialisé dans la boucle), aucun verrou ni attente (seuls les atomiques de swift-atomics), aucun appel système ni Objective-C (`print`, `Date()`), aucune libération d'objet (clips en `Unmanaged`, rendus par la file de retour ; types traversant les files triviaux, vérifiés par `_isPOD`), travail borné par échantillon, valeurs non finies ignorées, échauffement à l'`init`, déterminisme, mention « Fil audio uniquement ».

### Fils et rôles (architecture §3.1)

- Un seul fil de contrôle (`send`, `latestSnapshot`, `drainReleasedClips`) et un seul fil de rendu à la fois (`render` ou `pump`) ; `RoleGuard` déclenche une assertion en débogage si la règle est violée.
- Le fil de rendu ne dépile une commande que s'il reste une place dans la file de retour (un `load` renvoie au plus un clip).
- `pump()` applique les commandes et publie un instantané sans rendre d'audio ni avancer `sampleTime`.

### Pièges connus

- **Ré-ancrage du CUE disque tenu.** Après le saut, `gripOffset` reçoit la correction de `discAngle` (recalage IC-09) **et** la position saute au CUE : le disque reste sous le doigt et la suite du geste part du CUE. Le test le vérifie en avançant le doigt d'un quart de tour après le rappel (+0,45 s).
- **Échauffement.** Le premier rendu instancie des métadonnées génériques et peut allouer : l'`init` rend un bloc silencieux hors du fil audio (architecture §6.1 règle 7) ; le compteur d'allocations ne s'arme qu'après.
- **Charge à 16×** : mesurer en configuration optimisée (`swift test -c release --filter RenderLoadTests`) ; en débogage, la mesure n'a pas de sens. Ne pas faire échouer la CI sur ce test.
- **Déterminisme** : les commandes doivent tomber aux mêmes frontières de tampon ; le scénario fixe la taille de tampon (256) et la chronologie en trames.
- **Touches prédites** : `DeckPhysics.touchMoved` les ignore ; leur emploi pour combler les famines (`FingerTrajectory`) relève du calibrage PO-07, hors de cette story.
